# ADR 006 — One layout, a smaller vocabulary, and indexes by rule

Date: 2026-10-07. Status: accepted by the owner. Supersedes the per-category
folder sets of ADR 002 and ADR 005 D1, the seed vocabulary of ADR 003 and ADR
005 D2, and ADR 001 D10's rule that `.irori/scope.json` is never committed.
Nothing here has been exercised against a real knowledge base.

## Context

irori changed under the template since ADR 002: it shows page properties from
`.property/property.json` (0.1.54), connects folders on the device into
`contents/` (0.1.62, the only kind of connection since 0.1.67), lets a
knowledge base rename its layers in `.irori/scope.json` (0.1.70), and generates
the graph index from the pages (0.1.24, irori ADR 008). On 2026-10-07 the owner
asked what the knowledge and contents structure should now be, ontology
included, "as simple as possible but complete".

Reading the template against irori showed three frictions and one excess:

- irori commits `.irori/scope.json` when it creates a knowledge base and keeps
  the layer names there, while this template ignored the file, so a renamed
  layer never reached another device.
- irori counts every root entry outside schema and contents as knowledge, so
  `README.md`, `GETTING-STARTED.md` and `docs/` showed as pages without a type.
- Indexes were maintained by agents line by line, the same kind of drift ADR 008
  removed from the graph index.
- Three folder sets and fifteen page types asked a writer to choose where and
  what before writing anything, and the graph drew only `uses` and `same_as`,
  so it stayed almost empty.

The owner accepted the proposal on 2026-10-07, answering three questions:
one layout for every category (yes), the seed vocabulary below (yes), and
whether to keep `.irori/ontology.json` declared tables (keep them).

## Decisions

### D1 — One layout; the category changes the discipline

`Knowledge_Base/` holds `journal/<year>/` (people's records, append-only, never
promoted), `wiki/` (everything this scope answers for, flat until an index
passes about 150 entries) and `ontology/` (generated by irori). Folders are
divided by who writes and under what discipline, and there are only two such
disciplines. `decisions/`, `entities/` and `policies/` are gone: the type tells
those pages apart. The category, read from `.irori/scope.json`, only sets who
confirms pages and whether `verified` is required. `init` no longer fills a
**Folders** block in `AGENTS.md`.

### D2 — Each `contents/` mount keeps `Inbox/`, `source/` and `output/`

Already the organisation picture's premise (2026-09-11); now stated in the
contract with the page each folder corresponds to: nothing yet for `Inbox/`,
`reference` for `source/`, `artifact` for `output/`. A file that matters
without a page is what `ingest` looks for.

### D3 — The seed vocabulary: nine types, four relations

| Types | From before |
| --- | --- |
| `journal` | `daily`, `meeting`, `weekly` |
| `concept` | `concept`, `synthesis` (an answer filed back is a concept titled by its question) |
| `decision`, `reference`, `artifact` | unchanged |
| `policy` | `policy`, `standard` |
| `person`, `org`, `project` | unchanged; `repo` and `product` are left to a vocabulary review when a scope needs them |

Relations: `about` (a page to the person, organization or project it
concerns), `part_of` (a record to the organization or project it belongs to),
`uses` and `same_as` (unchanged). `about` and `part_of` make the records the
graph's hubs, which answers irori ADR 008's "revisit if the typed graph is too
sparse" before it arises. The five folded names are in `avoid`, so lint
replaces them in an existing knowledge base and no agent writes them again.

### D4 — The ontology has three parts with one owner each

The vocabulary (`.property/property.json`, the person through lint's
vocabulary review), the instances (each page's `type` and `relations`, agents
and people) and the index (`Knowledge_Base/ontology/`, irori). A table people
keep by hand without a page per row stays declared in `.irori/ontology.json`
(owner, 2026-10-07; irori ADR 008 D4).

### D5 — Indexes follow from the pages by one rule

`AGENTS.md` **Indexes** states the rule: the root keeps its frontmatter,
`# Folders` first with descriptions a person writes once, then one section per
declared type in declaration order, one line per page in file-name order, and
nothing else. irori 0.1.86 and later apply it with **索引を更新**; an agent
applies it to the folders it touched; lint checks it. Hand-written prose in an
index is no longer kept. `journal/` lists its years under `# Folders`, not
`# Years`.

### D6 — `.irori/scope.json` is committed; `README.md` is schema

The file carries the knowledge base's identity and layer names, and irori
0.1.86 and later take a pulled change to it that keeps the `scopeId`. The
template repository itself holds none, so copies do not share an identifier.
`README.md` is the repository's front page, which irori 0.1.86 and later count
as schema. `GETTING-STARTED.md` is folded into it, and `init` removes `docs/`,
this repository's own records, from a new knowledge base.

## Consequences

- A writer chooses between two folders and nine types. A scope that needs
  `repo`, `product` or a finer journal type adds it through a review.
- With an irori older than 0.1.86, an agent or lint writes the indexes, and
  pulled `scope.json` changes are refused as before.
- An existing knowledge base made from the earlier template keeps its folders,
  since folders are free; `lint` renames the folded types, and its index check
  rewrites `# Years` and hand-ordered indexes by the rule.
- The links from `README.md` and `CLAUDE.md` to this repository's records are
  GitHub URLs, so they survive `init` removing `docs/`.
